# 发布工作流

这个仓库只有一条长期主线：`main`。每个可说明、可验证、可回退的阶段发布一个语义化版本，不再维护与 GitHub 分离的“展示副本”。

## 版本边界

- `PATCH`（例如 `v1.1.1`）：修复缺陷，不改变产品能力。
- `MINOR`（例如 `v1.2.0`）：增加向后兼容的场景、内容或管理能力。
- `MAJOR`（例如 `v2.0.0`）：发生不兼容的数据结构、部署或交互架构变化。

视觉草稿、测试失败或尚未闭环的实验只提交到工作分支，不打版本标签。

## 每次发布

1. 将一项完整变化整理为原子提交，提交信息说明用户可感知结果。
2. 运行后端、静态、JavaScript 语法、世界表面和建造模式契约测试。
3. 检查待上传文件，不提交 `.env`、`.room-data/`、数据库、密码、令牌或个人媒体。
4. 更新 `DEVELOPMENT_HISTORY.md`，再创建带说明的语义化版本标签。
5. 推送 `main` 和版本标签，等待 GitHub Actions 全部通过。
6. 只有通过同一套测试的提交才允许部署；部署版本必须能追溯到 Git 标签和提交哈希。

## 长期约束

- GitHub 仓库 `randomcarol/lake-room-digital-world` 是唯一公开版本源。
- 本地运行目录必须跟踪同一仓库，禁止再次复制出另一套独立 Git 历史。
- 3D 房间、AI 国际学校和合唱团现阶段仍是独立应用；通过传送门和共享协议连接，不直接合并源码。
- 后台内容和世界状态属于数据，不与程序代码一起提交；生产数据变更要单独备份。
